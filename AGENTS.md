# Правила работы по поручению владельца

- Работайте прямо в `main`. Не создавайте ветки, worktrees для разработки или PR, пока владелец явно не изменит это правило.
- Сохраняйте посторонние изменения в рабочем дереве. Не используйте reset, force push и переписывание истории.
- Перед применением исторического ТЗ изучите актуальные исходники и тесты. Доведите до рабочего сценария runtime и UI, а не только интерфейсы или моки.
- Не возвращайте `/help`; сохраняйте горячие клавиши на главной.
- Для изменений UI показывайте превью настоящего OpenTUI: кадры терминального интерфейса, а не сгенерированные макеты.
- Выполняйте проверки качества проекта и подходящие проверки установленных пакетов и compiled-сборок. Сообщайте фактические результаты и явно указывайте непроверенные платформы.
- Пишите сообщения, пользовательскую документацию и заметки к релизам по-русски. Технические имена API, команд и параметров сохраняйте без перевода.

## Обязательная синхронизация CLI и Desktop

ChiselCode и [ChiselCodeDesktop](https://github.com/TheAsrada/ChiselCodeDesktop) — две оболочки одного продукта. Любое добавление, исправление или изменение сначала оценивайте для обеих версий. Просьба изменить CLI включает необходимую адаптацию Desktop в рамках того же задания; не оставляйте её отдельным предложением «сделать позже».

Перед реализацией прочитайте [порядок совместной разработки и выпуска](docs/contributors/desktop-sync.md), `AGENTS.md`, `engine.lock.json`, `docs/engine-updates.md` и `docs/releases.md` в Desktop. Найдите соседний checkout `ChiselCodeDesktop`; если его нет, получите репозиторий в отдельную соседнюю папку на `main`. Не заменяйте существующий checkout и сохраняйте его посторонние изменения. Если доступ отсутствует, продолжайте доступную работу и прямо сообщите, какая часть синхронизации заблокирована.

- Runtime, tools, providers, permissions, approvals, sessions, storage migrations, MCP, skills, команды и управление задачами реализуйте в ChiselCode. Desktop использует общий engine и публичный SDK; дублирование логики и импорт внутренних `ChiselCode/src` в renderer запрещены.
- При изменении общего поведения проверяйте `src/desktop/server.ts`, публичный протокол/SDK и соответствующий сценарий Desktop. Если capability требует управления или отображения, добавляйте клиентскую часть и проверки в том же задании. Совместимое исправление ядра может не требовать изменения React, но требует проверки и переноса в следующий закреплённый engine.
- Сохраняйте совместимость wire-событий, методов и DTO, общих профилей, credentials и истории. Изменение внутреннего runtime event не должно незаметно менять desktop-контракт. Несовместимость оформляйте явно через версию протокола/SDK и согласованное обновление клиента.
- Изменение только OpenTUI не требует аналогичной графической правки, но проверьте общую семантику и зафиксируйте причину отсутствия desktop-изменений. Уже документированные различия интерфейсов сохраняйте; новую общую возможность нельзя объявлять доступной в Desktop без рабочего сценария.
- Обновляйте документацию и `CHANGELOG.md` обоих проектов по их фактическому влиянию. Невыпущенные изменения записывайте в `Unreleased`; не редактируйте прошлую версию так, будто новое поведение уже входило в её установщики.
- До просьбы о релизе не публикуйте выпуск ради обновления lock. `engine.lock.json` ссылается на настоящий опубликованный release; до его появления явно записывайте ожидающее обновление ядра в Desktop `Unreleased`. Не придумывайте source commit, hashes или фиктивный tag.
- Проверяйте изменённое ядро из текущих исходников и compiled binary. GUI acceptance на старом закреплённом engine не подтверждает новое поведение. Новую клиентскую интеграцию проверяйте с соответствующим engine/SDK; порядок локальной проверки описан в руководстве.

## Просьба владельца «сделать релиз»

По умолчанию это поручение выпустить **оба проекта**: ChiselCode CLI и ChiselCode Desktop с этим же ядром. Дополнительное разрешение на второй выпуск не требуется. Исключение — явное поручение выпустить только один проект. Само изменение кода или этих инструкций не является просьбой о релизе.

1. Подготовьте код, документацию, оба CHANGELOG и проверки. Выберите новые свободные версии по SemVer; версия Desktop независима от CLI, текущий prerelease-канал сохраняется до явного изменения владельцем. Обновите связанные version/lock-файлы, где требуется.
2. Выполните проверки ChiselCode и дождитесь успешной native CI-матрицы **на выбранном release source commit**. Создавайте и отправляйте новый CLI tag только после этих результатов. Прошлый зелёный run и один локальный smoke их не заменяют.
3. Дождитесь успешного core Release workflow и публикации полного набора CLI installers, engine binaries, SDK, skills и `engine-manifest.json`. Проверьте tag/source/version, состояние assets и контрольные суммы.
4. В Desktop выполните `npm run update:engine -- v<новая-версия-CLI>`, `npm run sync:engine`, `npm ci`. Закрепите engine/SDK/skills из этого выпуска; внесите необходимые изменения клиента и документации. Системный CLI из desktop installer не заменяйте.
5. Выполните `npm run verify`, реальный GUI acceptance и проверки установленных payload. Дождитесь успешной Desktop native CI-матрицы на выбранном desktop release source commit для Windows x64, Linux x64 и macOS arm64/x64.
6. Только затем создайте и отправьте новый Desktop tag. Дождитесь Desktop Release workflow, загрузки всех установщиков, manifests/checksums и updater metadata, публикации выпуска. Проверяйте содержимое и provenance, а не только наличие страницы релиза.
7. Зафиксируйте пару версий и ссылки на оба выпуска в документации. В итоговом ответе укажите CLI version, Desktop version, встроенный engine, результаты проверок и реальные ограничения платформ/подписей.

Опубликованные tags и assets неизменяемы. Не создавайте tag заранее, не передвигайте его после ошибки и не перезаписывайте публичный выпуск: исправлению нужна новая свободная версия. Если CLI опубликован, а Desktop не прошёл, продолжайте исправление и выпуск Desktop на том же проверенном ядре; при исправлении самого ядра нужна новая CLI-версия. Пока второй выпуск не опубликован, совместный релиз не завершён — сообщите частичный статус и причину, сохранив рабочий предыдущий Desktop.
