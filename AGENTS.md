# Правила работы по поручению владельца

- Работайте прямо в `main`. Не создавайте ветки, worktrees для разработки или PR, пока владелец явно не изменит это правило.
- Сохраняйте посторонние изменения в рабочем дереве. Не используйте reset, force push и переписывание истории.
- Перед применением исторического ТЗ изучите актуальные исходники и тесты. Доведите до рабочего сценария runtime и UI, а не только интерфейсы или моки.
- Не возвращайте `/help`; сохраняйте горячие клавиши на главной.
- Для изменений UI показывайте превью настоящего OpenTUI: кадры терминального интерфейса, а не сгенерированные макеты.
- Выполняйте проверки качества проекта и подходящие проверки установленных пакетов и compiled-сборок. Сообщайте фактические результаты и явно указывайте непроверенные платформы.
- Пишите сообщения, пользовательскую документацию и заметки к релизам по-русски. Технические имена API, команд и параметров сохраняйте без перевода.

## Проверки: скорость и эффективность

- Выбирайте проверки по изменённому поведению и риску. Сначала запускайте подходящие точечные тесты. Для документации достаточно проверки текста, ссылок и примеров; для исправления одного сценария не повторяйте полный набор после каждого небольшого изменения.
- Полный source-набор выполняется один раз на ОС в `Quality`; проверки поставки — параллельно в `Packaging`, реальные серверы — в `Real Auto LSP`. Следуйте [порядку проверок](docs/contributors/testing.md). Успешную проверку на неизменном source не повторяйте без нового изменения, сбоя или конкретного нерешённого риска.
- Перед добавлением CI-step проверьте, не входит ли тот же fixture уже в `bun test` или другую проверку того же формата поставки. Installed и compiled smoke должны находить ошибки упаковки и запуска; не превращайте их в ещё одну копию всего source-набора. Удаляя дубль, указывайте, где остались его assertions и покрытие.
- В асинхронных UI-fixtures ожидайте видимый элемент, готовый ввод или фактический статус и задавайте конечный deadline. Фиксированная пауза сама по себе не подтверждает готовность к отправке клавиш и команд.
- Сохраняйте реальные проверки разрешений, путей/SSRF, отмены и cleanup, атомарной записи, конфликтов/revision, миграций и установленного runtime. Ускорение не оправдывает пропуск assertions, подмену реального сценария mock или скрытый отказ от проверки ОС. Не добавляйте тесты, которые лишь повторяют реализацию или проверяют безрисковую обратимую правку.
- Разносите независимые долгие проверки по jobs; используйте кэш скачанных зависимостей с закреплённым lockfile. Не переносите пользовательское хранилище, credentials или состояние тестовых сессий через CI cache. Измеряйте длительность jobs и общее время ожидания отдельно от суммарных runner minutes.
- При сбое сначала изучайте причину. Допускается один повтор неуспешного job на том же source при подтверждённом или предполагаемом временном сбое с честной записью результата. Повторяющийся сбой требует диагностики. Сетевые повторы внутри fixtures ограничивайте временной подготовкой зависимостей; ошибки функциональных assertions и активации должны оставаться ошибками. Не повышайте таймауты и не отключайте проверки ради зелёного статуса без объяснения и проверки конечной временной границы.
- Локальные точечные проверки и native CI дополняют друг друга. После успешной проверки расширяйте или повторяйте её только при новой причине. В отчёте указывайте source, выполненные проверки и непроверенные платформы; не выдавайте расчётное ускорение за измеренное.

## Документация, структура и навигация

Проверка документации обязательна в каждом задании, включая исправления и небольшие изменения. Выполняйте её вместе с работой над исходниками; актуальность, стиль и навигация входят в критерий завершения задания.

- Перед изменением прочитайте [README](README.md), [оглавление документации](docs/README.md) и руководства по затронутому сценарию. Сверьте описания с актуальным кодом, интерфейсом, конфигурацией, scripts и опубликованными версиями. Найденные в этих материалах неточности исправляйте в том же задании.
- При добавлении, исправлении или удалении поведения обновляйте связанные пользовательские руководства, архитектуру/API, разработку, установку и решение проблем по фактическому влиянию. Существенное изменение решения фиксируйте в принятом формате архитектурных решений. Дополняйте CHANGELOG в `Unreleased`; исторические записи и результаты проверок сохраняйте с их версиями и source commits.
- Сохраняйте единый русский стиль существующих руководств: конкретные действия, короткие связные объяснения, одинаковые названия сущностей и элементов UI. Команды, пути и API пишите точно как в реализации. Не добавляйте маркетинговые обещания, нейросетевые вводные, повторяющиеся пояснения и пустые разделы ради объёма.
- Стройте материалы вокруг задач читателя. Отделяйте пользовательские инструкции от устройства системы, истории реализации и будущих планов. Один документ посвящайте одному связному сценарию; длинные самостоятельные темы выносите в отдельные страницы с понятными стабильными именами.
- Поддерживайте маршрут `README.md → docs/README.md → тематическое руководство`. Каждая новая страница должна быть достижима из подходящего оглавления; добавляйте ссылку обратно к оглавлению и ссылки на связанные действия по необходимости. Корневой README оставляйте краткой точкой входа, а не копией всей справки.
- Соблюдайте последовательную иерархию заголовков без пропуска уровней, используйте списки для шагов и таблицы для сопоставлений. Группируйте пункты оглавления по задачам и аудитории; называйте ссылки по тому, куда они ведут, вместо «здесь» или «подробнее» без контекста.
- Не создавайте расходящиеся копии одной инструкции: поддерживайте основной материал и ссылайтесь на него. При переносе или переименовании страницы обновляйте оглавления, относительные ссылки, anchors, изображения и ссылки из другого репозитория; сохраняйте путь к новому материалу для ссылок из опубликованных releases.
- Различайте текущие исходники, опубликованный выпуск и roadmap. Не называйте возможность выпущенной до публикации и не объявляйте сценарий/платформу проверенными без результата. Проверяйте версии, имена установщиков, ограничения, миграции и примеры команд; секреты и пользовательские данные в примеры не включайте.
- Описывайте фактическую доступность возможностей в ChiselCode. Документацию концепта Desktop обновляйте только в рамках отдельного поручения по Desktop; наличие общей логики не расширяет задачу CLI на второй репозиторий.
- Перед завершением проверьте изменённые Markdown: относительные ссылки и anchors, существование изображений и целевых файлов, достижимость новых страниц из оглавления и соответствие примеров реальным scripts/API. Рискованные команды проверяйте в подходящем изолированном сценарии, не запускайте их на пользовательских данных ради примера. В итоговом ответе кратко укажите обновлённые материалы и фактические проверки; если справка не потребовала изменений, укажите конкретную причину.

## Desktop — отдельный концепт

[ChiselCodeDesktop](https://github.com/TheAsrada/ChiselCodeDesktop) пока является экспериментальным концептом. Изменения ChiselCode не требуют обновления Desktop, его engine lock, документации, GUI-проверок или выпуска. Не клонируйте и не открывайте второй репозиторий ради обычной задачи CLI.

Работайте над Desktop только по отдельному явному поручению владельца. В этом случае прочитайте его `AGENTS.md` и [порядок совместной разработки и выпуска](docs/contributors/desktop-sync.md). Общая runtime-логика остаётся в ChiselCode; клиент использует публичный protocol/SDK без копирования ядра и импорта внутренних `ChiselCode/src` в renderer. При изменении самого публичного контракта сохраняйте совместимость либо явно версионируйте несовместимость.

## Просьба владельца «сделать релиз»

По умолчанию это поручение выпустить **ChiselCode CLI**. Выпуск Desktop требует отдельного явного поручения; его состояние не блокирует выпуск CLI. Само изменение кода или этих инструкций не является просьбой о релизе.

1. Подготовьте код, документацию, `CHANGELOG.md` и проверки ChiselCode. Выберите новую свободную версию по SemVer и обновите связанные version/lock-файлы.
2. Дождитесь успешных обязательных jobs native CI **на выбранном release source commit** по [порядку проверок](docs/contributors/testing.md). Создавайте и отправляйте новый CLI tag только после этих результатов. Зелёный run другого коммита и один локальный smoke их не заменяют. Release повторно проверяет точный source и успешные jobs через GitHub API, затем собирает и проверяет поставку; полный source-набор повторно не запускается.
3. Дождитесь успешного Release workflow и публикации четырёх установщиков CLI и npm-пакета с SDK расширений. Служебные артефакты концепта Desktop в CLI release не публикуются. Проверьте tag/source/version, состояние assets и контрольные суммы.
4. Зафиксируйте версию и ссылку на выпуск в документации. В итоговом ответе укажите CLI version, результаты проверок и реальные ограничения платформ/подписей.

Опубликованные tags и assets неизменяемы. Не создавайте tag заранее, не передвигайте его после ошибки и не перезаписывайте публичный выпуск: исправлению нужна новая свободная версия. При отдельном поручении о совместном выпуске используйте порядок из руководства Desktop.
