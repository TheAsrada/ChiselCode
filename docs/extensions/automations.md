# Автоматизации расширений

[Разработка расширений](README.md) · [Управление расширениями](../extensions.md) · [Разрешения](../permissions.md)

Стандартный пакет объявляет `"requires": ["automations"]` в manifest и вызывает `context.automations?.register(definition)` во время `activate`. Для встроенного расширения используется та же форма регистрации. Контракт SDK v1 экспортирует `AutomationDefinition` и `AutomationSchedule`. Пакеты без этого требования продолжают использовать прежний API.

```ts
context.automations?.register({
  id: "daily-readme",
  schedule: { kind: "interval", firstAt: "2026-11-25T09:00:00Z", everyMs: 86_400_000 },
  tool: { name: "read_file", input: { path: "README.md" } },
});
```

Для одного запуска используйте `schedule: { kind: "once", at: "2026-11-25T09:00:00Z" }`. Время задаётся в UTC. Для интервала допустим период от одной секунды до 365 дней. Укажите устойчивый ID в пределах расширения. Для изменения времени или периода создайте новый ID. Зарегистрировать можно до 32 задач на активацию.

В расписании указывают штатный инструмент или инструмент этого расширения. Инструмент пакета адресуется как `ext:<extension-id>:<tool-name>`. Сборку примера можно проверить по [быстрому старту](quickstart.md). При запуске ChiselCode применяет политики проекта, Plan/Build и обычный запрос разрешения. Вложенный shell с `background: true` получает владельца активации и использует штатную очередь фоновых задач.

Расписание выполняется, пока рабочая область открыта в OpenTUI. Пассивные команды `extensions inspect` и `extensions status` показывают состояние пакета. При возвращении в проект просроченная разовая задача принимается один раз, а интервал объединяет пропущенные срабатывания в одно за последний наступивший срок. Активное выполнение завершится, прежде чем тот же ID примет новый запуск.

Управляйте паузой в **Настройки → Расширения → карточка расширения → Автоматизации**. Ручная пауза сохраняется между перезапусками и выключением расширения. При повторном включении ядро принимает только регистрации из новой активации. Последний принятый запуск и до 16 предыдущих записей остаются в локальном хранилище. Если приложение завершилось после принятия, но до записи результата, следующий процесс помечает запуск прерванным после подтверждения завершения владельца. Для неизвестного состояния процесса расписание остаётся защищённым от повторов.
