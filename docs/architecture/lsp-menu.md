## Навигация и владелец

Панель, F9 и Settings открывают один `OpenTuiLspSettings` в маршруте `tools.lsp`. Встроенное расширение получает только opaque `lspUiTarget`, проверяемый через WeakMap; доступ к контроллеру и контейнеру ему не передаётся. Generic view `analysis` удалён. Остальные представления расширений сохраняют общий механизм.

Оболочка сохраняет фокус и выбор панели; composer draft принадлежит прежнему владельцу. Меню начинает с текущего проекта, без папки — с общих настроек. Список и карточка открываются последовательно, чтобы один маршрут работал от 120×40 до 24×8. Native inputs сохраняют объект и курсор при resize. React и OpenTUI Core/React 0.5.12 сохранены. Руководства навыков адаптированы к установленным типам, включая различие `preventDefault` и `stopPropagation`; существующий input owner исключает передачу открывающего Enter новому экрану без искусственного ожидания.

## Разрешение и стратегия

Общий `enabled` отделён от `mode:auto/custom`. Legacy `mode:off` остаётся абсолютным запретом; включение нормализует его атомарно. Непустой старый `servers` без `mode` по-прежнему означает custom. При добавлении ручной записи новое меню явно сохраняет текущую стратегию, чтобы прежний default Auto не переключился скрыто.

Порядок индивидуального значения: project override → global override → `servers[id].enabled` или builtin `true`. Общие global/project Off ограничивают результат; затем применяются стратегия, язык, наличие записи и точное доверие. Индивидуальное разрешение не выдаёт trust и не включает Auto backend в custom. Неизвестный ID виден как недоступный. Strict `serverOverrides` принимает только проверенные ID и `{enabled:boolean}`, до 128 записей. `auto` и `auto-*` не становятся ручными executable-конфигурациями.

Сброс включения проекта удаляет только `enabled` и legacy `mode:off`; сброс сервера — только его override. Удаление ручного сервера очищает global override, проектные ссылки остаются видимыми. Стратегия, argv, initialization/settings и trust не теряются при обычном Off → On и перезапуске приложения.

## Данные и запись

`LspSettingsStore.load()` строит отдельный readonly management snapshot из каталога, effective конфигурации и `managementEntries()`. Для каждой записи передаются происхождение, языки, разрешение/источник, применимость, lifecycle/reason и все экземпляры по корням. Документы сохраняют current/observed/pending/stale/unavailable. Признак enabled не объявляется работающим процессом; пустой observed результат не становится подтверждением отсутствия ошибок. Публичные поля tools и strict `UiSnapshot` не переименованы.

`setEnabled`, `setServerEnabled` и `setStrategy` захватывают scope, root, configPath и revisions. Global patch обновляет свои поля через сериализованное хранилище. Project writes сериализуются по canonical root, сохраняют неизвестные секции и повторно сверяют файл перед atomic rename, включая Windows retry того же временного файла. Ручная форма сохраняется явно. Подписка на runtime обновляет evidence отдельно от baseline/draft; polling не добавляется. Quick patch обновляет revisions формы, сохраняя её несохранённые поля. Внешний конфликт отклоняет запись и оставляет draft; явное обновление данных позволяет проверить его перед повторным сохранением.

Ошибка записи не меняет сохранённое состояние. Ошибка применения после записи возвращает сохранённую конфигурацию с отдельным `applicationError`; меню сообщает, что завершение процесса не подтверждено, и предлагает повторить. Новые запросы остаются запрещены сохранённым Off. Cleanup сохраняет ссылку на transport до подтверждённого завершения; отказ dispose можно повторить.

## Выполнение и отмена

Общий app helper готовит `prepareUiToolInvocation(scope, "builtin.lsp", "restart", args, assertOwner)` и ставит `ui_tool` в существующую очередь. Сохраняются configPath, origin root/generation, owner signal, режим и разрешения, fingerprint recheck и checkpoints ToolExecutor. На главной используется project-operation owner. Модель и ключ не требуются; Plan/deny/Dont Ask и смена владельца сохраняют ограничения. В карточке Plan явно объясняет недоступность запуска. Шесть инструментов и диагностический context provider сохранены; пользовательские LSP-команды отсутствуют.

При выключении service сначала запрещает и инвалидирует все затронутые entries, затем ожидает cleanup. Поздние preparation/initialize/request callbacks не публикуют ready и диагностику. Подготовка встроенного TS учитывает потребителей общей распаковки: отмена одного workspace сохраняет соседа, последний отменяет работу и очищает staging. Включение не запускает процесс; следующий запрос создаёт новую generation. Один отменённый caller не останавливает общий сервер соседнего запроса.

Публичный engine/SDK protocol сохранён. Изменения CLI не требуют обновления отдельного концепта ChiselCodeDesktop.
