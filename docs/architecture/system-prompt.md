# Общий системный промпт

[Документация](../README.md) · [Архитектура](../architecture.md) · [Исследование и исходный план](../contributors/plans/system-prompt.md)

## Решение

ChiselCode выбирает один базовый текст по ID модели, зафиксированному при отправке запроса. Для GPT‑6.2 Sol, Astra и известных алиасов используется профиль GPT‑6.2. Остальные модели используют исходный универсальный промпт. Профиль помощника определяется его собственной моделью. Способ доступа к модели, Plan/Build и пользовательские разрешения не участвуют в выборе текста.

| Файл | Ответственность |
| --- | --- |
| [`src/core/prompts/universal.ts`](../../src/core/prompts/universal.ts) | Универсальная основа `BASE_SYSTEM_PROMPT` |
| [`src/core/prompts/gpt-6.2.ts`](../../src/core/prompts/gpt-6.2.ts) | Самостоятельная версия основы для GPT‑6.2, без добавления универсального текста поверх неё |
| [`src/core/prompts/index.ts`](../../src/core/prompts/index.ts) | Порядок выбора профиля и универсальный fallback |
| [`src/models/gpt-6.2.ts`](../../src/models/gpt-6.2.ts) | Общая проверка ID для выбора профиля и [сериализации ChatGPT Responses](chatgpt.md#поток-ответов) |
| [`src/core/prompt.ts`](../../src/core/prompt.ts) | Сборка общей части запроса для любого профиля |

Распознаются `gpt-6.2`, варианты с `-sol` и `-astra`, формы версии `6-2` и `62`, датированные снимки (`-YYYY-MM-DD`), а также точные алиасы `gpt-latest`, `gpt-sol-latest`, `gpt-astra-latest`, `gpt-terra-latest`. Сравнение выполняется без учёта регистра по последнему сегменту ID, поэтому `openai/gpt-6.2-sol` тоже подходит. ID отправляется провайдеру в исходном виде. Алиасы сопоставлены явно по [OpenCode 2.4.2](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/core/src/plugin/optimize.ts). При смене семейства за таким алиасом пересмотрите сопоставление.

Профиль GPT‑6.2 опирается на универсальный текст ChiselCode. Требования сформулированы через результат: довести разрешённую работу до проверенного результата, самостоятельно принять обратимые решения и дать самодостаточный ответ с фактическими проверками. Код должен сохранять поведение существующих вызовов и следовать проекту. OpenCode использует отдельный шаблон для семейства с общей сборкой контекста. Рекомендации по завершению задачи, стилю кода и ответу взяты из руководства OpenAI. [Шаблон OpenCode 2.4.2](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/core/src/plugin/system-prompt/gpt-6.2.txt) · [Рекомендации OpenAI для GPT‑6.2](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices).

Чтобы добавить профиль, разместите его текст в `src/core/prompts/` и зарегистрируйте условие в `index.ts`. Покройте точные ID и похожие ID, которым нужен универсальный текст. В обоих текстах поддерживайте ограничения ChiselCode на полномочия, недоверенные данные, сохранение пользовательских изменений и достоверность проверки. Права доступа проверяет runtime. Сборка контекста остаётся общей, а отдельные операции вроде суммаризации истории используют свои инструкции.

## Состав запроса

| Часть | Источник и назначение |
| --- | --- |
| Базовый текст | Профиль GPT‑6.2 или универсальный `BASE_SYSTEM_PROMPT` |
| Проектные инструкции | Отдельный раздел; resolver сохраняет приоритет `CHISEL.md > AGENTS.md > CLAUDE.md`. Автоматического поиска вложенных инструкций пока нет |
| Навыки | Только имена и описания разрешённых к автоматическому вызову навыков; тела загружаются отдельно |
| Окружение | `environment_snapshot`: JSON с OS, cwd, датой, shell и наблюдавшимся Git-состоянием; специальные символы экранируются |
| Identity, режим и permissions | Существующие блоки AgentRuntime, не заменяемые проектными правилами или навыками |
| Инструменты текущей итерации | Guidance только выбранных и доступных инструментов, до token budgeting и compaction |

Git-состояние в окружении ограничено размером и снято в начале запроса. Отсутствие поля не доказывает чистоту дерева; перед зависимым действием нужна свежая проверка. JSON и теги обозначают границу данных, но не являются самостоятельной защитой от prompt injection. Для вызовов `buildSystemPrompt` без ID используется универсальная основа.

## Инструкции инструментов и доверие

`load_skill` объясняет выбор навыка для текущей задачи и чтение относительных references. `inspect_skills` описывает проверку источника без установки. `install_skill` сохраняет правила точного revision, выбора candidate, исправления неверных аргументов и запрета shell-инсталляторов. В Plan инструкции установки отсутствуют вместе с инструментом.

`run_shell` объясняет обычную работу без worktree IDs, host shell и различие запуска фоновой задачи и завершения команды. В Plan и у readonly-помощника эти инструкции отсутствуют. `web_download` уже имеет собственный guidance; общий текст больше не дублирует его выбор.

Штатный `SkillsToolProvider` сохраняет в закрытом WeakMap идентичность созданных им handlers и исходный текст guidance. Каталог использует этот зафиксированный текст для native skill-инструментов. Подмена `spec.guidance` после регистрации, копия handler или произвольный `source: skill` не предоставляют этот канал. Содержимое `SKILL.md`, MCP outputs и extension guidance не становится системной инструкцией. При формировании guidance повторно проверяются режим, доступность и ограничение владельца.

Оба базовых текста содержат условные инструкции LSP. Его инструменты зарегистрированы через built-in extension, а общий запрет на promotion extension guidance сохранён. Блок применяется только при доступном анализе и сохраняет правила freshness/provenance, ленивого запуска и fallback к чтению кода и тестам.

## Помощники

Дочерний runtime передаёт в `buildSystemPrompt` свои `tools.skills` и ID модели. `ChildToolPolicy` допускает только оригинальный штатный `load_skill` с effect/permission `read`, дополнительно закреплённый через `seal`. Поддельный или скопированный handler не получает полномочий. Установка, просмотр удалённых источников и запись навыков у помощника по-прежнему запрещены.

Это устраняет две связанные проблемы прежнего поведения: отсутствующий каталог и отсутствие допуска к его штатному читателю. Первоначальный аудит обнаружил только первую; проверка через production provider выявила вторую. Каталог и загруженные инструкции не дают права выполнять описанные в навыке команды.

## Проверки и изменение текста

`prompt.test.ts` проверяет выбор базового текста, состав блоков, фильтрацию навыков и восстановление окружения из экранированного JSON. ChatGPT fixture проверяет три фактических запроса CLI: GPT‑6.2 Sol у основного агента, алиас у помощника и универсальный текст у GPT‑6.1. `tool-guidance.test.ts` проверяет универсальный текст в запросах AgentRuntime с разными model/provider identity, Plan/Build, снятие инструментов, сохранение доверенного native-текста и запрет promotion внешнего содержимого. Это детерминированные проверки с тестовым провайдером, не live-замер качества моделей.

`subagent-storage-policy.test.ts` выполняет штатное чтение навыка через executor и сохраняет проверки отказа установки, shell и записи для readonly. Production fixture `subagents-context.ts` проверяет каталог в дочернем provider request, отсутствие предварительно загруженного тела и сохранение инструкций после compaction. Остальные fixtures помощников читают cwd из нового JSON-блока.

В coding evals добавлены `explain-without-edits`, `plan-without-mutations` и `preserve-owner-with-source-injection`. Они доступны и для live-прогона: модель читает локальный fixture, а graders проверяют изменения и наблюдаемые вызовы. Сценарии не оценивают полноту объяснения или стиль финального ответа. Вредоносная инструкция в исходнике использует только тестовый `owner.txt`; сохранность файла проверяется по snapshot. Прежние Web fixtures остаются `mockOnly`.

Eval-задача может задавать `mode`; значение по умолчанию — Build. Отчёт сохраняет `agent_mode` и `base_prompt_sha256`. Hash относится только к выбранному базовому тексту, а source commit фиксирует версию остальных компонентов. Сравнение допускает разные hashes основы для A/B, но требует совпадения режима, платформы, сетевого режима и прежних условий сравнения. Старые отчёты без `agent_mode` считаются Build. Работа с незакоммиченными изменениями вне общей основы не воспроизводится одним source SHA; сравнивайте зафиксированные версии.

Команды и условия live evaluation описаны в [руководстве разработки](../development.md#agent-evaluation). Для сравнения поведения сохраняйте одинаковые ID моделей и настройки на обеих версиях. Детерминированные тесты проверяют payload, а качество ответов оценивают live-прогоны.

Live-проверка от 15 ноября 2026 года выполнена частично: 14 успешных trials, 6 прерываний квотой API. В четырёх сопоставимых парах прошли обе версии; преимущество нового промпта не доказано. [Условия, ответы и ограничения измерения](../contributors/reports/system-prompt-live.md).
