# Общий системный промпт

[Документация](../README.md) · [Архитектура](../architecture.md) · [Исследование и исходный план](../contributors/plans/system-prompt.md)

## Решение

ChiselCode использует одну общую основу и одинаковые правила сборки для всех моделей. Выбор provider ID, model ID или семейства не подключает другой поведенческий текст. Имя фактически выбранной модели остаётся данными `runtime_identity`. Различия сериализации API и лимитов обрабатываются драйверами и ContextManager.

Общая основа в `src/core/prompt.ts` задаёт работу по поручению, приоритет инструкций в пределах runtime, сохранение чужих изменений, проверку результатов и ответ на языке пользователя. Запрос объяснения или ревью не означает поручение править файлы. Для реализации агент должен довести разрешённую работу до проверки и сообщить фактический результат. Необоснованные идентификаторы, результаты тестов и обход отказов запрещены инструкциями; исполнимые ограничения дополнительно проверяются кодом.

Это изменение текущих исходников. Оно не гарантирует одинаковое качество всех моделей и не добавляет поддержку API, отсутствующую в драйвере. Проверка payload подтверждает состав запроса; качество поведения требует live evaluation.

## Состав запроса

| Часть | Источник и назначение |
| --- | --- |
| Общая основа | `BASE_SYSTEM_PROMPT`: одинаковая для всех моделей |
| Проектные инструкции | Отдельный раздел; resolver сохраняет приоритет `CHISEL.md > AGENTS.md > CLAUDE.md`. Автоматического поиска вложенных инструкций пока нет |
| Навыки | Только имена и описания разрешённых к автоматическому вызову навыков; тела загружаются отдельно |
| Окружение | `environment_snapshot`: JSON с OS, cwd, датой, shell и наблюдавшимся Git-состоянием; специальные символы экранируются |
| Identity, режим и permissions | Существующие блоки AgentRuntime, не заменяемые проектными правилами или навыками |
| Инструменты текущей итерации | Guidance только выбранных и доступных инструментов, до token budgeting и compaction |

Git-состояние в окружении ограничено размером и снято в начале запроса. Отсутствие поля не доказывает чистоту дерева; перед зависимым действием нужна свежая проверка. JSON и теги обозначают границу данных, но не являются самостоятельной защитой от prompt injection. Публичная сигнатура `buildSystemPrompt` сохранена.

## Инструкции инструментов и доверие

`load_skill` объясняет выбор навыка для текущей задачи и чтение относительных references. `inspect_skills` описывает проверку источника без установки. `install_skill` сохраняет правила точного revision, выбора candidate, исправления неверных аргументов и запрета shell-инсталляторов. В Plan инструкции установки отсутствуют вместе с инструментом.

`run_shell` объясняет обычную работу без worktree IDs, host shell и различие запуска фоновой задачи и завершения команды. В Plan и у readonly-помощника эти инструкции отсутствуют. `web_download` уже имеет собственный guidance; общий текст больше не дублирует его выбор.

Штатный `SkillsToolProvider` сохраняет в закрытом WeakMap идентичность созданных им handlers и исходный текст guidance. Каталог использует этот зафиксированный текст для native skill-инструментов. Подмена `spec.guidance` после регистрации, копия handler или произвольный `source: skill` не предоставляют этот канал. Содержимое `SKILL.md`, MCP outputs и extension guidance не становится системной инструкцией. При формировании guidance повторно проверяются режим, доступность и ограничение владельца.

Условный блок LSP остаётся в общей основе. Его инструменты зарегистрированы через built-in extension, а общий запрет на promotion extension guidance сохранён. Блок применяется только при доступном анализе и сохраняет правила freshness/provenance, ленивого запуска и fallback к чтению кода и тестам.

## Помощники

Дочерний runtime передаёт в `buildSystemPrompt` свой `tools.skills`. `ChildToolPolicy` допускает только оригинальный штатный `load_skill` с effect/permission `read`, дополнительно закреплённый через `seal`. Поддельный или скопированный handler не получает полномочий. Установка, просмотр удалённых источников и запись навыков у помощника по-прежнему запрещены.

Это устраняет две связанные проблемы прежнего поведения: отсутствующий каталог и отсутствие допуска к его штатному читателю. Первоначальный аудит обнаружил только первую; проверка через production provider выявила вторую. Каталог и загруженные инструкции не дают права выполнять описанные в навыке команды.

## Проверки и изменение текста

`prompt.test.ts` проверяет состав блоков, фильтрацию навыков и восстановление окружения из экранированного JSON. `tool-guidance.test.ts` проверяет одинаковые поведенческие инструкции в настоящих запросах AgentRuntime с разными model/provider identity, Plan/Build, снятие инструментов, сохранение доверенного native-текста и запрет promotion внешнего содержимого. Это детерминированные проверки с тестовым провайдером, не live-замер качества моделей.

`subagent-storage-policy.test.ts` выполняет штатное чтение навыка через executor и сохраняет проверки отказа установки, shell и записи для readonly. Production fixture `subagents-context.ts` проверяет каталог в дочернем provider request, отсутствие предварительно загруженного тела и сохранение инструкций после compaction. Остальные fixtures помощников читают cwd из нового JSON-блока.

В coding evals добавлены `explain-without-edits`, `plan-without-mutations` и `preserve-owner-with-source-injection`. Они доступны и для live-прогона: модель читает локальный fixture, а graders проверяют изменения и наблюдаемые вызовы. Сценарии не оценивают полноту объяснения или стиль финального ответа. Вредоносная инструкция в исходнике использует только тестовый `owner.txt`; сохранность файла проверяется по snapshot. Прежние Web fixtures остаются `mockOnly`.

Eval-задача может задавать `mode`; значение по умолчанию — Build. Отчёт сохраняет `agent_mode` и `base_prompt_sha256`. Hash относится только к общей основе, а source commit фиксирует версию остальных компонентов. Сравнение допускает разные hashes основы для A/B, но требует совпадения режима, платформы, сетевого режима и прежних условий сравнения. Старые отчёты без `agent_mode` считаются Build. Работа с незакоммиченными изменениями вне общей основы не воспроизводится одним source SHA; сравнивайте зафиксированные версии.

Команды и условия live evaluation описаны в [руководстве разработки](../development.md#agent-evaluation). Обе сравниваемые версии должны быть общими для всех выбранных моделей; индивидуальной подстройки промпта нет. Не выдавайте scripted success за улучшение качества LLM.
