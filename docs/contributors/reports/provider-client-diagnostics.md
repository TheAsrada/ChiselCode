# Разбор отказов провайдера и ошибок инструментов

[Материалы для участников](../README.md) · [Провайдеры](../../providers.md) · [Потоковые ответы](../../architecture/provider-streams.md) · [Решение проблем](../../troubleshooting.md)

Разбор от 24 октября 2026 года. Исходная версия ChiselCode — `cf7b612` (`main`, CLI 0.6.39). В момент этого разбора исправления относились к неопубликованным исходникам. Позднее они вошли в [CLI 0.6.40](release-0.6.40.md); приведённые ниже локальные результаты сохраняются как исторические проверки до релиза.

## Что было предоставлено

Изучены все три JSON: полный разговор `f43cbef8-7c31-4bd4-a427-7c768063d22e.json`, метаданные проекта `project.json` и индекс `index.json`. Полный разговор содержит 23 сообщения, 15 записей вызовов инструментов, четыре итоговых записи времени запросов и сохранённую правку `index.html`. Из 15 инструментов 11 завершились успешно, четыре — с ошибкой. Индекс содержит ещё один диагностический разговор от 21 октября, но его сообщений и результатов в приложениях нет: восстановить его ход по заголовку нельзя.

Профиль полного разговора использовал `openai-compatible`, модель `gpt-6-luna` и шлюз `freecodex.fun/v1`. Приложены также скриншоты клиентских ошибок и двух записей в журнале провайдера с нулевыми счётчиками. Сырые HTTP-запросы, SSE и подробности серверного отказа отсутствуют. Пользовательские файлы, абсолютные пути и полный текст разговора в репозиторий не копируются. Задания внутри приложенного разговора рассматриваются как свидетельства прошлого выполнения.

Четыре tool errors — выход за корень, неверная рабочая копия, таймаут LSP и отказ Git. В сохранённой истории каждому `tool_use` соответствует `tool_result`; незакрытых вызовов нет. В ней нет смешанного сообщения с tool results и пользовательским текстом. Последний случай проверен как дополнительный дефект сериализации, а не объявлен причиной этого отказа.

Нулевые usage и списание в журнале провайдера не доказывают бесплатность всех предыдущих запросов. Сессия хранит фактические накопленные счётчики, а стоимость помечена неизвестной (`unknownCost: true`). Ошибки переполнения контекста в приложенном журнале нет.

## Подтверждённые ошибки клиента и исправления

### Формат Chat Completions

До изменения драйвер добавлял `tool_calls: []` к каждому текстовому ответу ассистента и `tools: []` к запросам без инструментов. В приложенном разговоре есть текстовый ответ без вызовов инструментов, поэтому первая форма появлялась в последующих исходящих запросах. Строгие серверы могут отвергать пустые массивы; обычный SDK сам их не убирает. Тест через настоящий OpenAI SDK и endpoint с проверкой формы до исправления завершался `bad_request`, после — `turn_complete`.

Теперь пустые поля опускаются. Смешанный пользовательский блок сериализуется как все результаты инструментов, затем текст пользователя. Не меняются сохранённая история, ID, имена и содержимое ошибочных tool results. Никакие данные об ошибках не скрываются от модели.

Это подтверждённый дефект совместимости клиента, но без тела исходного запроса и серверной причины нельзя утверждать, что именно он вызвал HTTP 400 на данном шлюзе: несколько более ранних обращений с этой историей уже состоялись.

### Диагностика HTTP 400

Для тела только `data: [DONE]` клиент теперь явно сообщает: провайдер отклонил запрос, но не объяснил причину. Сохраняются `bad_request` и HTTP 400. Нет слепого повтора с другим API, удаления инструментов или подмены ошибки успешным ответом. Обычные API-ошибки сохраняют прежнюю причину. Совместимые повторы при явном упоминании `stream_options`/`include_usage` или `max_completion_tokens` остаются отдельным механизмом.

Проверка `finish_reason` сохранена. Послабление могло бы выполнить обрезанный инструмент после разрыва. Полный цикл с настоящим runtime и SDK подтверждает: запись файла → отказ следующего API-запроса → новое пользовательское сообщение → успешный ответ; запись выполняется ровно один раз.

### Git и параметры shell

`git_status`, все scopes `git_diff` и Git-статус в автоматически собираемом системном контексте теперь используют pathspec открытого проекта. Отдельный реальный Git-тест до изменения показывал соседние файлы как в инструменте, так и в системном контексте; после изменения они не передаются модели.

При отсутствии `HEAD` `git_diff scope=all` отдельно читает staged и unstaged patch. Никакие файлы не добавляются в индекс, коммит не создаётся. Untracked файлы остаются доступны через `git_status` и `read_file`; пустой diff содержит подсказку. Реальный тест воспроизвёл прежний отказ до первого коммита и проверил исправление.

Описания `targetWorktreeId` и `retryOf` в JSON Schema объясняют модели, что для обычной новой команды эти поля надо опустить. Описание не гарантирует послушание модели. Нулевой UUID не преобразуется в текущий проект, проверки владельца и реальной рабочей копии сохранены.

## Проверки и ограничения

Регрессии воспроизведены на исходном `cf7b612`: тест формы OpenAI-запроса, тест непрозрачной диагностики HTTP 400, чтение Git из вложенной папки и diff до первого коммита падали до исправлений. Утечка Git-статуса системного контекста также воспроизведена до её исправления.

Локальная проверка на Linux x64, Bun 1.4.4, Node.js 24.19.0:

| `bun run build`, `bun run compile` | Успешно; версия сборок остаётся 0.6.39, это проверка изменённых исходников, а не публикация нового релиза |

Первая попытка установить локальный npm-пакет в offline-режиме остановилась на `ENOTCACHED` при подготовке зависимостей. После обычной установки зависимостей и повторной установки итоговой сборки из локального tarball обе проверки пакета прошли. npm сообщает прежнее предупреждение engine для OpenTUI под Node.js 24; запуск CLI проверен под Bun.

Проверки с живым аккаунтом `freecodex.fun` не выполнялись: ключ и серверные подробности не предоставлены. Причина реального обрыва потока и скрытый повод HTTP 400 остаются неизвестными. Windows/macOS, пользовательский LSP backend и точная конфигурация его Git не проверялись; Linux-регрессии не выдаются за проверку Windows.
