## Цель и границы

Пользователь управляет LSP из единого меню через панель: видит, включён ли анализ, какие серверы доступны и работают, может выключать весь анализ или конкретный сервер, смотреть диагностику и восстанавливать сервер после ошибки. Пользовательские `/lsp-status` и `/lsp-restart` удаляются. Инструменты LSP для агента сохраняются.

Основной маршрут — **боковая панель → Меню → Анализ кода · LSP**. Строка LSP в F9 / «Состояние сервисов» и существующий раздел настроек ведут в тот же интерфейс. Это несколько входов в одно меню с общей моделью данных, действиями и правилами сохранения.

Соблюдать [AGENTS.md](../../../AGENTS.md): работа в main; русский интерфейс и документация; горячие клавиши на главной; без возвращения `/help`; настоящие кадры OpenTUI при реализации. Для реализации применены закреплённые в AGENTS.md `opentui` с opentui.com (API), `opentui-design` (навигация/ввод/состояние) и `tui-visual-design` (компоновка/читаемость), с адаптацией к React и установленным API. Проект закрепляет OpenTUI Core/React 0.5.12; обновление зависимостей для этой задачи не требуется. Репозиторий ChiselCodeDesktop вне задачи.

Важные действующие свойства:

- Отсутствие LSP-конфигурации означает Auto. Непустой старый `servers` без `mode` означает custom. Global off ограничивает все проекты; project `enabled:false` выключает отдельный проект.
- Открытие настроек, status и поиск не запускают сервер и не скачивают SDK. Первый запрос diagnostics/navigation запускает подходящий сервер. Один отменённый caller не должен остановить общий сервер другого запроса.
- Сохранение Off вызывает refresh существующих scopes, блокирует затронутые entries, инвалидирует данные и закрывает процессы. Это основа для новых переключателей, а не поведение, которое нужно писать заново.
- Ручной сервер требует доверия к точному canonical root. Переключение режима/сервера не выдаёт доверие. Явный restart проходит Build/process permissions; Auto read-навигация доступна в Plan.
- Diagnostics различают current, observed, pending, stale и unavailable. TS без document version даёт observed; пустой ответ не подтверждает отсутствие ошибок. Сохраняется анализ tracked документов, а не обещание проверки всего проекта.

## Проблемы текущего UX и модели

1. **Два разных окна управления.** Из панели открывается окно анализа с диагностикой; полная конфигурация находится в Settings. Пользователь должен понимать внутреннее разделение, чтобы найти выключение.
2. **Нет индивидуальных переключателей встроенных серверов.** Auto-каталог — информационные строки. `enabled` существует у ручных серверов, но в Auto нельзя выключить, например, Python отдельно от TypeScript.
3. **Нет цельного списка фактических состояний.** Settings получает список живых entries и каталог, но рисует преимущественно каталог и один общий status. `status()` без ID выбирает preferred либо стандартный Auto backend; общий индикатор не заменяет состояние каждого сервера и каждого корня в monorepo.
4. **Смена режима проекта циклическая.** Enter перебирает inherit → auto → custom → off, а не показывает варианты явно. Исходная область — глобальная, хотя пользователь часто хочет управлять текущим проектом.
5. **Рабочее действие зависит от удаляемой команды.** После удаления регистраций `/lsp-restart` кнопка Settings сломается, если не заменить её внутренний путь.
6. **Состояние сервиса смешано с наличием проверок.** В `lsp-ui.ts` отдельный пользовательский текст для disabled отсутствует; Off может сопровождаться «нет проверок». Недоступность, выключение и ожидание запроса должны объясняться по-разному.
7. **Операции и технические параметры смешаны.** Каталог, запуск, формы executable/argv, trust и диагностика должны иметь разные уровни подробности в одном понятном маршруте.

- В исследованной dev-версии есть общая настройка `lsp: true/false` и индивидуальное `disabled:true` по имени сервера. Включённый сервер запускается при обращении к подходящему файлу.
- Новый вариант конфигурации заменяет либо дополняет предыдущий согласно типу настройки. Для ChiselCode нужно явно определить собственные правила global/project и показать источник результата в интерфейсе.
- В этой dev-версии документация описывает LSP по умолчанию выключенным. В ChiselCode по умолчанию Auto. Просьба о переключателях не требует менять существующий default: в плане сохраняется Auto.
- Изученный GUI OpenCode показывает список LSP и подписи enabled/disabled; отдельного switch непосредственно в этих строках нет. Поэтому новый интерфейс ChiselCode — собственное решение под требуемый сценарий, а не заявление о копировании готового экрана OpenCode.

## Предлагаемое меню

### Вход и общий обзор

Панель → «Анализ кода · LSP» открывает сразу управление. F9 и Settings открывают тот же компонент и контроллер. Старое generic-окно `analysis` больше не является вторым местом управления; диагностика переносится в общее меню. Для открытия используется узкая core-navigation capability, аналогичная существующим opaque `backgroundUiTarget` / `agentsUiTarget`; расширению не выдаётся доступ к контроллеру или контейнеру приложения.

В шапке видны проект и область применения: **Этот проект** / **Все проекты**. Для выбранной папки первая область — «Этот проект»; без папки доступны общие настройки и действие «Выбрать проект». Основная строка — **Анализ кода: Включён / Выключен**, с указанием «Наследуется» или «Изменено для проекта». Возврат к наследованию — отдельное действие.

Рядом короткое объяснение: «При включении сервер запускается при следующем запросе анализа». Если анализ выключен глобально, проектный переключатель блокирован с переходом к общим настройкам. У переключателя области всегда явная подпись, чтобы выключение проекта нельзя было спутать с выключением для всех.

### Список серверов

Каждая строка содержит название, языки, переключатель и фактическое состояние. Каталог стандартных серверов и настроенные ручные записи имеют явные подписи происхождения. Поиск по названию/языку; по умолчанию показываются работающие/использованные в этом workspace и ручные записи, с доступным пунктом «Все поддерживаемые серверы». Полный каталог не исчезает при пустом workspace.

Переключатель означает разрешение использовать сервер, а не состояние процесса. Для включённого, ещё не вызванного сервера показывается «Ждёт запроса», а не «Работает». У недоступного backend — причина: платформа, SDK, пути или доверие. Выключенный сервер остаётся в списке, чтобы его было понятно как включить обратно.

Для нескольких project roots одного сервера строка агрегирует количество экземпляров и ошибок; подробности показывают каждый корень. Выключение сервера в workspace останавливает все его entries в этом workspace. Это не выключает остальные языки.

### Подробности сервера

Enter открывает карточку с названием, фактическим состоянием, областью настройки, project roots и диагностикой. Основные действия: «Включить/Выключить», «Перезапустить» либо «Запустить сейчас», «Настройки». Для ошибки показываются причина и действие восстановления. В Plan недоступность явного запуска объясняется в самой карточке; restart не обходит действующий режим.

Версии, capabilities, поколение и пути находятся в «Технических деталях». Ручная конфигурация — отдельная форма внутри этого же маршрута: executable, argv, языки/расширения, проверка путей; initialization/settings и список доверенных roots раскрываются дополнительно. Включение ручного сервера не подтверждает доверие проекту.

Диагностика показывает файл, строку, сообщение и свежесть. «Нет результатов проверки», «Данные устарели» и «Нет ошибок в подтверждённом результате» — разные состояния. Нельзя превращать observed/unavailable в зелёное «Ошибок нет».

### Ввод и сохранение

- ↑/↓ выбирают строку; Enter открывает подробности; Space меняет выбранный переключатель. В native input/textarea эти клавиши принадлежат редактированию.
- Tab / Shift+Tab меняют зоны фокуса; Ctrl+F открывает локальный поиск; PgUp/PgDn прокручивают список; мышь выполняет те же действия.
- Esc выходит на предыдущий уровень, затем возвращает в исходную панель. Закрытие восстанавливает фокус, выбранную строку и черновик чата.
- Простые переключатели сохраняются сразу узким patch. Пока запись и остановка применяются, видно «Применяется…»; окончательное состояние показывается после результата. Ошибка не изображается как успешное выключение.
- Ручная форма сохраняется явно: «Сохранить» / Ctrl+S, ошибки и незавершённый draft не теряются. Быстрый переключатель не должен неявно сохранять или стирать другие поля формы. При конфликте revisions сохраняется draft и предлагается обновить данные.
- На широком терминале список и подробности могут быть рядом; на узком — последовательно с видимой кнопкой «Назад». В 24×8 остаются заголовок, текущая строка и доступ к основным действиям через прокрутку.

## Семантика переключателей и совместимость

До переписывания UI закрепить контракт схемами и тестами:

1. Global Off — абсолютный запрет для всех проектов. Project Off — запрет только выбранного canonical workspace. Для индивидуального сервера project override имеет приоритет над global значением, пока весь LSP не выключен глобально. Отсутствие override означает наследование.
2. Добавить типизированные overrides по ID для встроенных серверов; проектные overrides должны поддерживать также существующие ручные серверы. Не помещать builtin ID в нынешний `global.servers`: там требуются executable/trust и запрещены `auto-*`.
3. Сохранить совместимость `mode:auto/custom/off`, project `enabled:false`, `serverId` и legacy custom без mode. Новые UI-переключатели не должны терять выбранную стратегию и настройки ручного сервера после Off → On или перезапуска приложения. Для этого отделить флаг включения от стратегии при нормализации конфигурации; legacy Off читается как выключение. Имена новых полей закрепить вместе со схемой, не имитируя JSON OpenCode поверх существующей схемы.
4. Auto/custom остаются стратегиями выбора, скрытыми в дополнительных настройках. Одновременный выбор builtins и произвольных custom, изменение каталога и скачивание новых языков сверх текущих возможностей не входят в эту переделку.
5. Disable сразу блокирует новые обращения, отменяет подготовку/initialize/request затронутых entries, инвалидирует их diagnostics/context и дожидается штатного cleanup дерева процессов. Поздний ответ либо поздний initialize не возвращает ready. Незатронутые серверы и проекты продолжают работу.
6. Enable восстанавливает разрешение, не скачивает SDK и не запускает процесс. Следующий реальный запрос запускает сервер лениво. Явный «Запустить сейчас» / restart остаётся действием через ToolExecutor и разрешения.
7. Toggle сохраняет конфигурацию и кэш установки. Это не удаление пакета, не отзыв доверия и не очистка пользовательских данных.

### Планируемый контракт конфигурации

Следующий контракт принят в реализации; описание требований сохранено для сопоставления с исходной базой.

| Поле | Глобальная конфигурация | Конфигурация проекта |
| --- | --- | --- |
| `enabled?: boolean` | Новый общий флаг; при отсутствии действует прежняя семантика `mode` | Существующий флаг; `false` выключает проект, `true` разрешает работу в пределах глобального запрета |
| `mode?: auto/custom/off` | Сохраняется; новое меню пишет `auto/custom` как стратегию, `off` читается для совместимости | Сохраняется; отсутствие наследует стратегию, прежний `off` означает отключение |
| `servers` | Существующие ручные executable/trust-конфигурации сохраняются | Запуск и доверие по-прежнему не разрешается задавать из проекта |
| `serverId` | Не добавляется | Существующий выбор ручного сервера, без смены назначения поля |
| `serverOverrides?: Record<serverId, { enabled: boolean }>` | Новый набор индивидуальных значений для встроенных и настроенных ручных серверов | Новый набор проектных значений с приоритетом над глобальным значением конкретного сервера |

Для нового общего выключения писать `enabled:false`, сохраняя стратегию и все серверные настройки. Включение меняет флаг на `true`; состояние сохраняется между запусками. Старый `mode:off` при включении нормализовать в том же атомарном patch: для глобального scope восстановить custom при наличии ручных записей, иначе Auto; для проектного scope восстановить custom при `serverId`, иначе наследование. Исторически выбранная до legacy Off стратегия в файле не хранится; интерфейс не обещает восстановить неизвестное значение.

Наследование включения и выбор стратегии — отдельные свойства. «Наследовать» для общего проектного переключателя удаляет только его `enabled` и legacy `mode:off`; ручная стратегия, `serverId` и индивидуальные значения сохраняются. Возврат конкретного сервера к наследованию удаляет только его запись из проектного `serverOverrides`. Полный сброс проектной секции не является побочным эффектом одного переключателя.

Индивидуальное разрешение вычисляется так: project override → global override → прежний `servers[id].enabled` для ручного сервера либо `true` для builtin. Общие global/project Off проверяются до этой цепочки. Затем применяются стратегия, язык, существование записи и доверие. Project override может изменить индивидуальное глобальное значение, но не выдать доверие, обойти общий global Off или включить Auto-сервер в режиме custom.

`serverOverrides` проходит strict-схему с `LspServerIdSchema`, только полем `enabled` и конечным пределом записей. Неизвестный ID не запускает процесс и показывается как недоступная запись с возможностью удалить override. Builtin IDs, включая `auto` и `auto-*`, не превращаются в ручные executable-конфигурации. Удаление ручной записи также очищает её глобальный override; оставшиеся проектные ссылки показывают, что сервер больше не настроен.

Пример глобальной настройки: Auto разрешён, Python выключен по умолчанию.

```json
{
  "lsp": {
    "mode": "auto",
    "enabled": true,
    "serverOverrides": {
      "auto-python": { "enabled": false }
    }
  }
}
```

Пример проектного исключения: разрешить Python для этой папки. При глобальном выключении всего LSP это исключение не действует.

```json
{
  "lsp": {
    "serverOverrides": {
      "auto-python": { "enabled": true }
    }
  }
}
```

### Представление данных и запись из меню

Сформировать отдельный внутренний readonly snapshot управления: scope/root, общий effective enabled и его источник, стратегия, revision, список серверов. Для каждого сервера передавать ID, происхождение, языки, effective enabled и источник, применимость к текущей стратегии, причины блокировки, экземпляры по project root и свежесть diagnostics. Не вычислять «работает» из одного флага enabled или отсутствия ошибок.

Нынешние `LspStatus.servers` и `LspStatus.catalog` использовать как исходные данные, сохраняя существующие поля инструментов. Новый snapshot отдавать через узкий settings/action port; не расширять произвольными полями strict `UiSnapshot` общих расширений и не экспортировать mutable entries сервиса. При изменении внутреннего DTO проверять фактические потребители в CLI и SDK; публичные поля не переименовывать ради нового экрана.

Быстрые действия оформляются отдельными операциями `setEnabled`, `setServerEnabled`, сбросом конкретного override и подпиской на изменения. Они захватывают scope, canonical root, configPath и revisions. Global patch пишет только принадлежащие действию поля через существующее сериализованное хранилище; project patch сохраняет остальные `.chiselrc`-секции и повторяет проверку версии перед rename. Конкурентный внешний edit не перезаписывается полной копией из меню.

Для переключателя различать результат сохранения и применения runtime. Если файл сохранён, а cleanup завершился ошибкой, показывать «Выключено в настройках; завершение процесса не подтверждено» и действие повтора. Не возвращать молча переключатель во включённое состояние, будто запись не состоялась, и не утверждать, что процесс остановлен. Пока применение не завершено, новые обращения остаются запрещены. После успешного quick patch обновлять baseline/revision формы без потери несохранённых полей. Если quick patch затрагивает редактируемое поле, показать конфликт, сохранив draft.

## Проверки реализации

## Критерии готовности

Пользователь открывает меню из панели, за одно действие выключает LSP текущего проекта и видит завершение его серверов; включает обратно без немедленной установки/запуска. Может отдельно выключить один сервер и продолжить анализ другим. Находит диагностику, ошибку и восстановление в том же меню. Понимает область применения и наследование. Ни кнопки, ни сообщения не требуют `/lsp-*`; команды отсутствуют в списке. Данные чужого проекта и старого поколения не появляются. Существующая ручная конфигурация продолжает работать с прежними ограничениями доверия.

Обязательные приёмочные сценарии:

1. **Два языка:** запустить TS и Python в одной папке, выключить Python, подтвердить завершение его entries и успешную навигацию TS; включить Python, подтвердить отсутствие процесса до нового запроса, затем успешный анализ.
2. **Наследование:** global Auto → индивидуальный Python Off → проектный Python On; затем global Off блокирует оба языка и оба проекта. Возврат project override к наследованию меняет только выбранный override.
3. **Гонка выключения:** выключить сервер во время подготовки, initialize и запроса; поздний callback не создаёт ready, не возвращает диагностику и не меняет переключатель нового владельца. Указанные сценарии проверяются раздельно, а не только остановкой уже готового процесса.
4. **Ручная настройка:** настроенный custom с точным trust переживает Off → перезапуск приложения → On с прежними argv/стратегией. Отозванный trust остаётся отозванным, даже если project override разрешает сервер.
5. **Ввод и владелец:** из панели открыть меню, поиск, карточку и форму; сменить раздел, размер терминала и вернуться. Черновик чата и формы сохраняется, Enter не отправляется в чат; поздний результат старого root не подменяет новую папку.
6. **Ошибки применения:** отказ записи оставляет сохранённое состояние; успешная запись с ошибкой cleanup показывает различие, запрещает новые запросы и позволяет повторить завершение. Конфликт с внешним `.chiselrc` сохраняет обе несвязанные секции и пользовательский draft.
7. **Удалённые команды:** `/lsp-status` и `/lsp-restart` отсутствуют в descriptors/autocomplete; кнопки status/restart работают через настоящий tool path без model request. Assertions Plan/deny/Dont Ask и persistence выполняются после удаления команд.
