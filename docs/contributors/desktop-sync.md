# Совместная разработка и выпуск CLI и Desktop

Обязательные правила агента находятся в [AGENTS.md](../../AGENTS.md). Этот порядок применяется при работе в [ChiselCode](https://github.com/TheAsrada/ChiselCode) и [ChiselCodeDesktop](https://github.com/TheAsrada/ChiselCodeDesktop): изменения общего продукта доводятся до обеих оболочек, а просьба владельца «сделай релиз» означает выпуск обоих проектов, если явно не указан только один.

## Перед изменением

1. Проверьте `main`, `git status` и актуальность обоих checkout. Сохраните чужие правки и изучите инструкции обоих репозиториев. Для отсутствующего репозитория используйте соседнюю папку, а не development branch/worktree.
2. Прочитайте [архитектуру общего ядра](../architecture/desktop.md), Desktop `engine.lock.json`, `docs/engine-updates.md`, `docs/protocol.md`, `docs/features.md` и `docs/releases.md`.
3. Сравните текущие CLI version/source и закреплённый Desktop engine. Неперенесённые изменения общего поведения включите в текущую синхронизацию; не заменяйте их старой проверкой Desktop.
4. Определите, что меняется в runtime, desktop-адаптере, публичном SDK, GUI, общей конфигурации и сессиях. Это часть выполнения задания, а не отдельное согласование с владельцем.

## Что переносить

| Изменение в ChiselCode | Действие для Desktop |
| --- | --- |
| Исправление runtime, provider или обычного tool при сохранении контракта | Проверить адаптер и реальный сценарий; включить исправление в следующий закреплённый engine без копирования реализации |
| Новая общая capability, настройка или команда | Предоставить данные/управление через публичный API; проверить generic UI либо добавить нужный клиентский сценарий |
| DTO, wire event, enum, error code, approval или lifecycle | Согласовать protocol/SDK и клиент, проверить старые поддерживаемые сценарии; несовместимость версионировать явно |
| Профили, credentials, sessions, миграция или блокировки | Проверить оба процесса на одном ChiselCode Home/проекте, чтение старых данных и определённую совместимость writers |
| Только компоновка, горячие клавиши или оформление OpenTUI | Проверить отсутствие влияния на общую семантику; указать, почему Desktop не требует правок |
| Документация, workflow или упаковка | Обновить затронутые инструкции, ссылки, manifests и проверки; не приписывать установщикам невыпущенное поведение |

Новые общие возможности должны быть доступны через Desktop в рамках того же задания. Если графическое действие уже поддерживается динамическим каталогом или generic tool card, подтвердите это проверкой. Уже описанные в Desktop `docs/features.md` различия оболочек не означают, что будущую общую возможность можно автоматически оставить только в терминале.

## Проверка до релиза

Для изменения общего runtime используйте настоящий source и compiled engine из текущего ChiselCode:

```sh
bun run desktop:smoke
bun run desktop:engine
bun tests/fixtures/desktop-server.ts ./dist/chisel-engine
```

Выполните также подходящие unit/integration checks и штатные проверки качества. Для поведения UI нужны реальные кадры OpenTUI/Electron и сценарии ошибок, подтверждения, отказа и отмены.

Если меняется клиент Desktop, проверяйте его с engine и SDK этих же исходников. До изменения релизной версии можно собрать SDK командой `bun scripts/build-desktop-sdk.ts` и временно использовать generated engine/SDK/skills в игнорируемом Desktop `vendor`. Не меняйте сохранённый release lock и не отключайте production handshake/hash-проверки ради такого прогона. В отчёте укажите source commit и локальные незакоммиченные правки кандидата: одинаковая строка версии не делает candidate опубликованным engine.

После локального candidate-прогона восстановите `vendor` через `npm run sync:engine`, зависимости через `npm ci` и убедитесь, что временные файлы и изменения lock не попали в commit. Если версия кандидата отличается от закреплённой и штатный handshake его отклоняет, используйте отдельный явно обозначенный test/dev-сценарий; не выдавайте старое ядро за новое. Обязательный release GUI acceptance всё равно выполняется на окончательных опубликованных артефактах.

Основные desktop-команды:

```sh
npm run verify
npm run test:e2e
npm run package
node scripts/verify-installers.mjs
```

На Linux GUI требует display/Xvfb. Windows/macOS проверяются на соответствующих native runners. Проверка файла или cross-compiled binary не заменяет запуск установленного приложения.

## До просьбы о релизе

Доведите core/adapter/SDK/client изменения и подходящие проверки до согласованного состояния, закоммитьте относящиеся к заданию правки в обоих `main`, обновите документацию и `Unreleased`. Записи Desktop должны различать уже доступное поведение закреплённого engine и изменения, ожидающие следующего core release; при отсутствии влияния достаточно обоснования в итоговом отчёте.

Не публикуйте промежуточный CLI выпуск только ради Desktop lock без поручения о релизе. `engine.lock.json` остаётся привязанным к последнему подходящему опубликованному набору. В ответе прямо укажите, если изменения исходников готовы, но новая desktop-сборка с этим ядром ещё не выпущена.

## Совместный релиз

Версии CLI, Desktop, protocol, SDK и session schema решают разные задачи. Совместный выпуск не требует одинаковых номеров: он требует, чтобы Desktop содержал engine/SDK/skills точно выбранного CLI release.

1. Подготовьте обе release notes, версии и клиентскую совместимость. Проверьте, что новые tags свободны; незавершённый прежний tag не используйте повторно. Сохраняйте текущий канал stable/beta, пока владелец не поручит изменить его.
2. Дождитесь проверок выбранного CLI source в [CI](../../.github/workflows/ci.yml), затем создайте новый tag. [Release](../../.github/workflows/release.yml) должен проверить исходники и опубликовать полный набор CLI installers, engine для четырёх targets, SDK, skills и manifest.
3. Проверьте опубликованный core tag/source, version/protocol, состояние assets, hashes и их соответствие manifest. Только после этого выполните в Desktop:

   ```sh
   npm run update:engine -- v<версия-CLI>
   npm run sync:engine
   npm ci
   npm run verify
   npm run test:e2e
   ```

4. Закоммитьте новый `engine.lock.json`, связанные клиентские/lock/version правки, CHANGELOG и документацию в Desktop. Дождитесь его native main CI на точном release source: Windows x64, Linux x64, macOS arm64/x64, исходный GUI и установленные payload.
5. Создайте новый Desktop tag. Дождитесь успешной release-матрицы и публикации всех установщиков, blockmaps, updater metadata, `release-manifest.json` и `SHA256SUMS`. Сверьте встроенный engine/source с CLI release и опубликованные bytes с manifests.
6. После публикации добавьте в оба проекта ссылки на пару выпусков и фактические результаты. Теги остаются на проверенном release source; последующий документационный commit не меняет этот source.

Между двумя репозиториями нет атомарной публикации: Desktop скачивает артефакты уже опубликованного CLI. Если второй этап упал, не откатывайте и не перезаписывайте первый публичный release. Исправляйте Desktop и продолжайте; если понадобилось исправление ядра, выпустите новую версию CLI и закрепите её. Совместный выпуск завершён только после публикации обоих проектов.

## Отчёт о выполнении

Укажите изменения CLI и Desktop либо конкретную причину отсутствия клиентской правки; версии/source commit, использованные в проверках; фактические результаты и оставшиеся ограничения. При релизе добавьте ссылки на оба выпуска, пару CLI/Desktop versions, встроенный engine, platforms/installers и состояние подписей. Статус «синхронизировано» требует этих фактов, а не одинаковых номеров пакетов.

Эти инструкции задают порядок работы агента. Они не являются GitHub-ботом и не запускают выпуск сами при каждом commit или обновлении глобально установленного CLI.
